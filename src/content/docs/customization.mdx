Every colored loomi component resolves its colors through a shared set of CSS custom
properties. Override one of them from your own page CSS and **every component that uses
that color updates instantly** — no rebuild, no config file, and no Tailwind required on
your end.

## Overriding the defaults

The override hook is `--loomi-<color>-<shade>`, where `<color>` is one of the 14 palette
names and `<shade>` is a Tailwind-style tonal step (`50`–`950`).

```css
:root {
  --loomi-primary-600: #16a34a; /* every primary-colored component turns green */
  --loomi-primary-700: #15803d; /* …and its hover/active shade follows */
}
```

That's the entire API. Custom properties inherit straight through the Shadow DOM
boundary, so a single `:root` declaration reaches into every component on the page —
buttons, inputs, tags, alerts, all of it — at once.

<Aside type="tip" title="Override every shade you use">
  Most components reference more than one shade of a color (e.g. `600` for the fill,
  `700` for hover, `100` for a soft background). For a clean re-skin, override the full
  ramp for any color you're changing — `50` through `950`.
</Aside>

## The 14 palette colors

Each of these has its own independently overridable ramp:

```
primary    secondary   red      blue      green     purple    pink
orange     black       cyan     violet    indigo    fuchsia   gray
```

So `--loomi-red-500`, `--loomi-cyan-700`, `--loomi-gray-100`, etc. are all valid override
targets.

## Per-instance colors

Components like `<loomi-checkbox>`, `<loomi-tag>`, and `<loomi-badge>`-style elements
accept a `color` attribute so two instances can use different palette colors on the same
page:

```html
<loomi-checkbox color="red" checked>Critical</loomi-checkbox>
<loomi-checkbox color="green" checked>Resolved</loomi-checkbox>
```

Each instance still resolves through the same `--loomi-<color>-*` tokens internally, so
overriding `--loomi-red-600` re-skins every red-colored instance, not just one.

## Dark mode

loomi ships a `<loomi-theme-switcher>` component that toggles a `dark` class on
`<html>` and persists the choice to `localStorage`:

```html
<script type="module">
  import "@loomi/theme-switcher/loomi-theme-switcher.js";
</script>

<loomi-theme-switcher></loomi-theme-switcher>
```

<Tabs>
<TabItem label="Use the component">

Drop it anywhere in your layout — it handles light/dark/system state on its own:

```html
<loomi-theme-switcher light-text="Light" dark-text="Dark" system-text="Auto"></loomi-theme-switcher>
```

</TabItem>
<TabItem label="Drive it yourself">

Or call the exported helpers directly if you're building your own toggle UI:

```js
import { applyLoomiTheme, getLoomiTheme } from "@loomi/theme-switcher";

applyLoomiTheme("dark");   // "light" | "dark" | "system"
getLoomiTheme();           // reads the persisted choice
```

</TabItem>
</Tabs>

Style your dark theme against the `html.dark` class it toggles — typically by
overriding the same `--loomi-*` tokens with darker-mode-appropriate values:

```css
html.dark {
  --loomi-gray-50: #0f172a;
  --loomi-gray-900: #f1f5f9;
  /* …override whichever tokens your dark palette needs */
}
```

<Aside type="caution">
  Call `applyLoomiTheme(getLoomiTheme())` as early as possible in your page (before
  first paint) if you want to avoid a flash of the wrong theme before
  `<loomi-theme-switcher>` upgrades.
</Aside>

## Forking for deeper changes

The override model above covers the vast majority of theming needs. If you need to
change the *default* values themselves (rather than overriding them per-app), or add a
15th palette color, that requires building from source — loomi's defaults are generated
from a single `palette.json` at build time, so a fork only needs to edit one file and
rebuild. That's a source-level change, not something exposed to npm consumers.
