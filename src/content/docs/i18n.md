This document explains how LoomiUI's built-in translation system works and how to use
it when you're building or editing a component. It's written for contributors — if
you're an app developer *consuming* LoomiUI and just want to set a locale or override
some copy, see the "Internationalization" section of
`packages/core/README.md` instead; this page assumes you're
reading component source or sending a PR.

For the general contributor workflow (setup, adding a component, publishing), see
`CONTRIBUTING.md`. For right-to-left layout support, see the
[RTL Support](https://loomiui.com/rtl-support/) docs page — that's a separate concern
from everything below (see [Not RTL](#this-is-not-rtl-support)).

## How it fits together

Three pieces, each with one job:

- **`packages/core/src/i18n.ts`** is the shared lookup layer every component calls
  into — `loomiT()`, `loomiDefaultText()`, `setLoomiLocale()`, `getLoomiLocale()`,
  `defineLoomiTranslations()`, and the date/time helpers
  (`loomiDateFormatter`/`loomiMonthName`/`loomiWeekdayNames`). It contains no strings
  of its own.
- **`packages/core/src/locales/<code>.ts`** (`en.ts`, `ar.ts`, `de.ts`, `es.ts`,
  `fr.ts`, `it.ts`, `ml.ts`, `pt_BR.ts`, `tr.ts`, `zh_CN.ts`) are where the actual
  strings live, one file per language, aggregated into a `builtinTranslations` map by
  `src/locales/index.ts`. One file per language means adding or fixing a translation is
  a one-file diff in a language you actually read, with no risk of merge-conflicting
  with someone translating a different language in the same PR cycle.
- **A component's `locale` property** (every translatable component has one) picks
  which locale that *specific instance* resolves strings against, falling back to the
  page-wide default set by `setLoomiLocale()`.

`en.ts` is the only locale file that has to be complete — it's the final fallback for
every lookup, so it's also the closest thing this repo has to a canonical key list.
Every other locale file is allowed to be a partial subset; a key it's missing just
falls through to English instead of failing (see [the fallback chain](#the-fallback-chain-why-partial-locale-files-are-fine)
below). Most built-in locale files today only cover a fraction of `en.ts`'s keys — that's normal, not a bug you need to fix.

## Making a new component's copy translatable

This is the part you need for **adding or changing a component**, as opposed to
translating one — it's not currently spelled out in `CONTRIBUTING.md`, so read this
section even if you've contributed here before.

### 1. Add a `locale` property

```ts
@property() locale = "";
```

Leave it empty by default — an empty string tells `loomiT`/`loomiDefaultText` to fall
back to the shared page-wide locale (`getLoomiLocale()`, defaulting to `"en"`), so most
consumers never have to set it per-instance. Add it even if your component has no
translatable strings *yet*; it costs nothing and keeps the API consistent across
components.

### 2. Pick `loomiT` or `loomiDefaultText`

Use **`loomiT(path, params, locale)`** for a string that has no equivalent
user-settable attribute — aria-labels, dialog roles, anything purely internal to the
rendered markup:

```ts
// packages/input/src/loomi-input.ts
aria-label=${loomiT("common.clear", {}, this.locale)}
```

Use **`loomiDefaultText(value, defaultValue, path, locale, params?)`** instead when the
string is *also* a settable property/attribute (like `placeholder` or `label`) that
should keep working if a consumer sets it explicitly:

```ts
const DEFAULT_SEARCH_PLACEHOLDER = "Search emoji";

@property() placeholder = DEFAULT_SEARCH_PLACEHOLDER;

// ...in render():
const searchPlaceholder = loomiDefaultText(
  this.placeholder,
  DEFAULT_SEARCH_PLACEHOLDER,
  "emojiPicker.searchPlaceholder",
  this.locale,
);
```

`loomiDefaultText` only translates when `value === defaultValue` — i.e. the consumer
never touched the attribute. The moment someone sets
`<loomi-emoji-picker placeholder="Buscar…">`, that literal string wins over any
translation, in every locale. This is the pattern anywhere a prop needs to be
*both* overridable *and* translated by default — get it wrong (e.g. using `loomiT`
directly for the default and shipping the result as the property's default value) and
a consumer's `:root`-level locale switch won't affect an attribute they never touched.

### 3. Add the key(s) to `en.ts`

Pick one top-level namespace per component, camelCase, matching the component's own
identity (`emojiPicker`, `photoGallery`, `themeSwitcher`, ...). Nest further for
multi-part components (see `calendar.form.colors.primary` in `en.ts` for an example
of a deeply nested one). Reuse the shared **`common.*`** namespace
(`common.close`, `common.dismiss`, `common.remove`, `common.clear`, `common.loading`)
for generic actions instead of re-adding "Close"/"Dismiss" text under your own
namespace — over a dozen components already share these keys.

```ts
// packages/core/src/locales/en.ts
emojiPicker: {
  placeholder: "Pick an emoji",
  searchPlaceholder: "Search emoji",
  emptyText: "No emoji found",
  dialog: "Emoji",
},
```

That's the only locale file you're required to touch. Don't feel obligated to add the
same key to all 10 locale files in the same PR — see the fallback chain below.

### 4. Use `:param`-style placeholders for dynamic text

`loomiT`'s second argument fills `:name`-style tokens into the template string
(see `formatTemplate` in `i18n.ts` — it's a plain `replaceAll`, not a full ICU
implementation):

```ts
// en.ts
pagination: { totalLabel: "Showing :a to :b of :c" }

// call site
loomiT("pagination.totalLabel", { a: 1, b: 10, c: 42 }, this.locale)
// -> "Showing 1 to 10 of 42"
```

Some strings (`filepicker.placeholderLine2: "%s up to %s"`) instead use printf-style
`%s` tokens that the *component* substitutes itself, not `i18n.ts` — check how the
existing string is consumed before copying the pattern for a new one.

### The fallback chain: why partial locale files are fine

A lookup for locale `pt_BR` tries, in order: `pt_BR` → the base language `pt` → `en`.
So if you add a new key to `en.ts` only, every other locale instantly falls back to
your English string instead of rendering blank or throwing — nothing breaks, and no
other locale file needs touching in the same PR. Translating that key into other
languages is a welcome, but separate and optional, follow-up.

## Adding or fixing a built-in language

### Adding a brand-new built-in language

1. Copy `packages/core/src/locales/en.ts` to `<locale>.ts`, named for the locale code
   (e.g. `ak.ts` for Akan; use an underscore for region variants, the way `pt_BR.ts`
   does).
2. Translate every string **value** — keep every object/array key identical to
   `en.ts`. Leave `:placeholder`-style and `%s` tokens untouched; substitution happens
   at call time regardless of language. A partial file (a subset of `en.ts`'s keys) is
   completely fine — see the fallback chain above.
3. Import the new file in `packages/core/src/locales/index.ts` and add it to the
   `builtinTranslations` map.
4. Optionally add the locale code to the `LoomiLocale` union in `src/i18n.ts` — purely
   an editor-autocomplete nicety; the type also accepts any `string`, and the runtime
   lookup works regardless of whether it's listed.
5. `pnpm --filter @loomidev/core build` (or `pnpm build` from the repo root) to confirm
   it compiles, then add the locale code to the "Built-in locales" line in
   `packages/core/README.md`.

### Fixing or improving an existing translation

No aggregation step needed — edit the relevant `<locale>.ts` under
`packages/core/src/locales/` directly and rebuild `@loomidev/core`.

### Adding a language without touching this repo at all

Any consumer can register translations at runtime via `defineLoomiTranslations(locale,
translations)` (exported from `@loomidev/core`) without a PR here — see the
"Internationalization" section of `packages/core/README.md` for the consumer-facing
walkthrough. It deep-merges into whatever's already registered for that locale, so a
partial object covering only the keys someone cares about is fine. That's the right
path for a quick or unofficial translation; promote it to a real `locales/<x>.ts` file
(steps above) once it's complete and worth shipping as a built-in default.

## Date and time formatting

`loomiDateFormatter(locale, options)` wraps `Intl.DateTimeFormat` with LoomiUI's locale
normalization (`ar` / `de` / `zh_CN` → `zh-CN` for `Intl`, etc.) — prefer it over
constructing `Intl.DateTimeFormat` directly so locale resolution stays consistent
across components.

`loomiMonthName(locale, month, style)` and `loomiWeekdayNames(locale, weekStarts)`
check for a custom `datepicker.monthsShort` / `monthsLong` / `weekdaysShort` array
registered for that locale first (see the `defineLoomiTranslations` example in
`packages/core/README.md`), and only fall back to `Intl` formatting if none was
provided. `loomiWeekdayNames` also handles the Sunday-first vs. Monday-first rotation
(`weekStarts: "monday"` rotates the custom array by one instead of assuming `Intl`'s
own week-start convention) — reuse it rather than re-deriving weekday order in a new
component.

## This is not RTL support

Locale controls *which strings and date formats* render; it does not flip layout
direction. A component rendering Arabic copy via `locale="ar"` does not become
right-to-left on its own — RTL is a separate, explicit opt-in (`dir="rtl"`) covered in
the [RTL Support](https://loomiui.com/rtl-support/) docs page. Don't couple the two:
don't infer `dir` from `locale`, and don't gate RTL-specific CSS behind a locale check.

## Quick reference

- New component → add `@property() locale = "";` even before you have any strings to
  translate.
- String with no matching attribute → `loomiT(path, params, locale)`.
- String that's also a settable attribute/property → `loomiDefaultText(value,
  defaultValue, path, locale, params?)`.
- New key → add it to `en.ts` only. Don't block a PR on translating it into the other
  9 locales.
- Reuse `common.*` for generic close/dismiss/remove/clear/loading copy instead of a
  per-component duplicate.
- Fixing a translation → edit that one `locales/<code>.ts` file, rebuild
  `@loomidev/core`, done.
- Never infer RTL from `locale` — they're unrelated toggles.
