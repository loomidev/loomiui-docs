You customize LoomiUI with normal CSS variables, just like any other styles in your app.
Add the variables in your own stylesheet, and every LoomiUI component on the page can
pick them up automatically.

That means you can start small: change one color, preview it, and adjust as needed. When
you are happy with it, the same values apply across buttons, inputs, alerts, and more.

## Overriding the defaults

LoomiUI color tokens follow a predictable naming convention, making it easy to customize and override any palette color.

```txt
--loomi-<color>-<shade>
```

`<color>` is one of the palette colors below. `<shade>` is the strength of the color:
`50` is very light, `600` is the normal button color, and `950` is very dark.

For example, this changes the main `primary` color to green:

```css
:root {
  --loomi-primary-600: #16a34a;
  --loomi-primary-700: #15803d;
}
```

Once these variables are defined, any LoomiUI component that uses `color="primary"` automatically adopts your custom palette.

The change is applied consistently across the library, including [buttons](/components/button), [inputs](/components/input), [tags](/components/tag), [alerts](/components/alert), and any other component that relies on the primary color tokens.

Define your overrides on the `:root` selector to make them available throughout the document:

Variables declared in `:root` are globally accessible. LoomiUI components can resolve these values even when rendered inside Shadow DOM.

This approach lets you manage your application’s theme from a single stylesheet, ensuring a consistent look and feel without styling individual component instances.

<loomi-alert type="success" icon="check-circle">
  <strong>Tip:</strong> change the whole color ramp when you can. Components often use
  more than one shade: <code>600</code> for the main color, <code>700</code> for hover,
  and lighter shades for soft backgrounds.
</loomi-alert>

## The 14 palette colors

These are the built-in semantic + utility palettes available out of the box.
You can use any of these names with the `color` attribute across components.
For example:

```html
<loomi-button color="indigo">Open</loomi-button>
<loomi-tag color="orange">Draft</loomi-tag>
<loomi-alert color="red">Action required</loomi-alert>
```

Each palette in LoomiUI uses the same 11-step shade scale:
`50`, `100`, `200`, `300`, `400`, `500`, `600`, `700`, `800`, `900`, and `950`.

Because the scale is consistent, token names are always predictable. Any
combination of a supported color + one of these shade values is valid, for example:
`--loomi-red-500`, `--loomi-cyan-700`, or `--loomi-gray-100`.

If you override tokens for one of these colors (such as `--loomi-indigo-600`),
every component using that color updates automatically.

### How components use shades

Most interactive components map shades to states in a consistent way:

| Shade(s) | Usage |
| --- | --- |
| `600` | Base/primary action color |
| `700` | Hover and active state |
| `50`–`200` | Soft backgrounds, accents, and low-emphasis surfaces |
| `300`–`500` | Borders, outlines, and intermediate emphasis |
| `800`–`950` | High-contrast text and strong surfaces |

For best visual consistency, override the full shade ramp for a color instead of only
one or two tokens. Updating the complete set keeps buttons, tags, alerts, and form
controls visually aligned across all states.

## Per-instance colors

Use the `color` attribute when you want to apply a specific palette to an individual component instance.
This is useful when a single UI element needs semantic meaning (for example, danger, success, or warning)
without changing the global theme.

```html
<loomi-checkbox color="red" checked>Critical</loomi-checkbox>
<loomi-checkbox color="green" checked>Resolved</loomi-checkbox>
```

The `color` value must match one of the supported LoomiUI palette names (such as `red`, `green`,
`indigo`, or `primary`).

Because LoomiUI components resolve these values from CSS tokens, instance colors remain fully themeable.
If you later override a token like `--loomi-red-600`, every component that uses `color="red"` updates
automatically across the app. This lets you keep component markup simple while still getting centralized control over visual styles.

## Dark mode

LoomiUI supports runtime theme switching and dark-mode token overrides out of the box.
The recommended option is the built-in `<loomi-theme-switcher>` component, which handles
mode selection, persistence, and class application automatically.

The switcher supports three modes:

| Mode | Behavior |
| --- | --- |
| `light` | Always uses the light theme |
| `dark` | Always uses the dark theme |
| `system` | Follows the user’s OS/browser color-scheme preference |

## Install and render the switcher

Import the component once, then render it where users can access theme controls
(for example, your app header, profile menu, or settings page):

```html
<script type="module">
  import "@loomi/theme-switcher";
</script>

<loomi-theme-switcher></loomi-theme-switcher>
```

When dark mode is active, the switcher applies a `dark` class to the root `<html>` element.
LoomiUI components automatically resolve any token overrides declared under `html.dark`.

The selected mode is saved in `localStorage`, so the user preference is restored on
subsequent visits without extra setup.

### Customize switcher labels

Use [custom text labels](/components/theme-switcher/#custom-labels) when needed:

```html
<loomi-theme-switcher system-text="System"></loomi-theme-switcher>
```

### Use helper functions in custom UI

If you are building your own theme toggle, import the helpers:

```js
import { applyLoomiTheme, getLoomiTheme } from "@loomi/theme-switcher";

applyLoomiTheme("dark"); // "light" | "dark" | "system"
getLoomiTheme(); // reads the persisted choice
```

`applyLoomiTheme()` applies the selected mode and updates the root class.
`getLoomiTheme()` reads the currently persisted preference.

### Use your own theme system (no switcher)

If your app already has theme controls, you do not need `<loomi-theme-switcher>`.
LoomiUI only requires a `dark` class on an ancestor element (typically `<html>`).

For example:

```html
<html class="dark">
  <body>
    <loomi-button color="primary">Save</loomi-button>
  </body>
</html>
```

You can toggle the class directly:

```js
document.documentElement.classList.add("dark"); // turn dark mode on
document.documentElement.classList.remove("dark"); // turn dark mode off
```

For a persistent manual toggle, store the selected theme and apply it on load:

```js
const savedTheme = localStorage.getItem("theme");

if (savedTheme === "dark") {
  document.documentElement.classList.add("dark");
}

function setTheme(theme) {
  localStorage.setItem("theme", theme);
  document.documentElement.classList.toggle("dark", theme === "dark");
}
```

If your app uses a different class name (for example, `theme-dark`), place your LoomiUI
token overrides under that selector:

```css
html.theme-dark {
  --loomi-gray-50: #0f172a;
  --loomi-gray-900: #f1f5f9;
}
```

### Define dark-mode tokens

To customize dark mode colors, declare token overrides in `html.dark`:

```css
html.dark {
  --loomi-gray-50: #0f172a;
  --loomi-gray-900: #f1f5f9;
  /* …override whichever tokens your dark palette needs */
}
```

<loomi-alert type="warning" show-close-icon="false">To avoid a flash of the wrong theme on first paint, call <code>applyLoomiTheme(getLoomiTheme())</code> as early as possible during app startup.</loomi-alert>

## Forking for deeper changes

For most teams, CSS token overrides are the right and sufficient approach.
They are fast to ship, easy to maintain, and keep you on the official LoomiUI
upgrade path.

You should fork LoomiUI only when you need framework-level changes that cannot be
expressed with app-level CSS variables.

Common examples:

- Changing the default color values shipped to all consumers of your design system
- Adding a new built-in palette color beyond the standard 14 palettes
- Modifying how default tokens are generated at build time

These defaults are produced from `palette.json` during the LoomiUI build process.
As a result, this is a source-code customization workflow (inside a LoomiUI fork),
not a runtime theming workflow in your app.

If you only need product-level branding or per-app theme control, prefer token
overrides in your stylesheet instead of maintaining a fork.
